# Absen Kilat — Checkpoint, Tampilan Manager, Export Laporan, Reminder Absen

> **Untuk Hermes:** eksekusi per task dengan TDD (tes gagal → kode minimal → tes lulus → commit).
> Urutan yang disarankan: Epic A → B → C → D → E. Setiap epic bisa dirilis sendiri.

**Goal:** menutup empat celah operasional HR yang muncul saat uji lapangan: jam absensi yang
belum mengikat perilaku sistem, kejadian "lupa absen" yang tidak punya jalur resmi, manager
tidak punya pandangan timnya, dan laporan yang tidak bisa diolah sistem lain.

**Architecture:** Semua fitur menempel pada modul yang sudah ada (attendance, approvals, reports,
notifications) — tidak ada layanan baru. Approval checkpoint memakai pipeline approval yang sama
(`approval_status`, `approved_by`, `approved_at`, `rejection_reason`), hanya menambah
`source = "checkpoint"`. Tampilan manager memakai relasi `users.manager_id` yang sudah ada.
Export dibuat sebagai endpoint streaming di backend, bukan di frontend, agar bisa dipakai integrasi
mesin-ke-mesin.

**Tech stack:** Go 1.26 + chi + SQLite (backend), Next.js 16 (admin), Expo SDK 54 (mobile), GitHub Actions CI.

## 1. Temuan audit (fakta, bukan asumsi)

Diverifikasi langsung di `main` hari ini:

| Hal | Status sebenarnya |
|---|---|
| Setting jam absensi | **Ada di pengaturan**: `work_start` (09:00), `work_end` (17:00), `workdays`. Tersimpan di tabel `settings`, tervalidasi HH:MM, tampil di `/pengaturan`. |
| Apakah jam itu mengikat? | **Tidak.** `AttendanceService` memakai `cfg.CutoffHour` (int dari konfigurasi proses) untuk menandai `late`, dan `work_end` tidak dipakai sama sekali. Mengubah setting tidak mengubah perilaku absensi. |
| Blokir absen di luar jam | Tidak ada. `absen_mode` hanya `checkin_only` / lain; tidak ada penolakan berbasis jam. |
| "Lupa absen" (checkpoint) | Belum ada jalur resmi. Admin punya override (`PATCH /admin/attendance/{id}`) tapi itu tindakan admin, bukan permintaan karyawan. |
| Hierarki atasan | **Sudah ada**: `users.manager_id`, role `supervisor`, `ListByManager`, endpoint `GET /admin/team`. Belum ada daftar absensi tim. |
| Export laporan | **Belum ada.** Hanya JSON: `GET /admin/reports`, `GET /admin/reports/users`. Nol kode CSV/XLSX di repo. |
| Reminder | Belum ada. Notifikasi saat ini **in-app saja** (`notification_service`, migrasi 002); belum ada push (tidak ada `expo-notifications`). Issue lama **#12** menutup topik yang sama — tiket baru harus mereferensikannya. |
| Kolom pendukung | `attendances` sudah punya `approval_status`, `approved_by`, `approved_at`, `rejection_reason`, `source` (`app`/`qr`/`manual`), `notes`, `location_id`. `users` sudah punya `manager_id`, `notification_enabled`. |

**Konsekuensi desain:** tiga dari empat permintaan bisa dibangun tanpa migrasi besar — cukup satu
migrasi (tabel checkpoint + preferensi reminder) dan satu perubahan perilaku (jam kerja mengikat).
Tidak perlu tabel tim baru: `manager_id` sudah cukup untuk MVP.

## 2. Keputusan desain yang saya ambil (bisa dibantah)

1. **Checkpoint = attendance regularization.** Istilah industri untuk "lupa punch": di HRIS besar
   (Bynarize, KpiTravel dsb.) disebut *regularization* — karyawan mengajukan koreksi, atasan
   menyetujui, hasilnya jadi record kehadiran dengan jejak audit. Kita ikuti model itu, jangan bikin
   konsep sendiri.
2. **Checkpoint tidak menimpa record asli.** Dibuat record **baru** dengan `source="checkpoint"`
   dan `approval_status="pending"`; record lama (kalau ada) tetap utuh. Alasannya: audit. Kalau
   checkpoint disetujui untuk tanggal yang sudah punya record, record checkpoint yang dipakai
   untuk laporan, record lama ditandai superseded lewat `notes` (bukan dihapus).
3. **Checkpoint butuh alasan + lampiran opsional**, dan maksimal mundur **7 hari** (konfigurabel),
   maksimal **1 checkpoint per tanggal per user**. Ini menutup penyalahgunaan paling umum.
4. **Penyetuju checkpoint:** `manager_id` user → kalau kosong, fallback ke role `supervisor` (semua)
   → kalau tetap kosong, `hr`/`super_admin`. Ini menghindari checkpoint menggantung tanpa penyetuju.
5. **Jam kerja mengikat secara bertahap, bukan langsung memblokir.** Mode baru di setting:
   `attendance_window_mode` = `off` (perilaku sekarang), `mark` (tandai telat/early-leave, tetap
   boleh absen), `block` (tolak di luar jam + grace). Default **`mark`** supaya rilis tidak
   mematahkan kebiasaan kru lapangan; `block` diaktifkan HR setelah POC.
6. **Grace period** `late_grace_minutes` (default 10) — telat dihitung setelah jam mulai + grace.
7. **Export MVP = CSV** (streaming, tanpa dependency baru) + **XLSX** menyusul di tiket terpisah
   (butuh `excelize`). CSV sudah cukup untuk integrasi; XLSX demi kenyamanan HR.
8. **Reminder = lokal di perangkat (local notification), default OFF**, sesuai permintaan.
   Server-side push (FCM/APNs) tidak dikerjakan di rilis ini karena butuh kredensial push dan
   pipeline baru; dicatat sebagai tiket fase berikutnya. Konsekuensi yang harus diterima: reminder
   lokal hanya jalan kalau aplikasi pernah dibuka hari itu dan izin notifikasi diberikan.

## 3. Open questions (jawab sebelum task terkait dimulai)

1. **Jam kerja per lokasi atau global?** Sekarang global. Untuk klien dengan beberapa proyek
   (shift berbeda), jam per lokasi lebih benar — tapi menambah kolom di `locations` dan prioritas
   resolusi. Saran: global dulu di rilis ini, per lokasi masuk fase shift.
2. **`block` dipakai untuk siapa?** Kalau dipakai, siapa yang boleh menembus? Saran: role
   `supervisor`/`hr` selalu boleh + otomatis jadi checkpoint pending.
3. **Export: siapa yang boleh unduh?** Saran `hr`/`super_admin` saja; supervisor hanya timnya
   (kalau nanti perlu).
4. **Reminder jam berapa & berapa kali?** Saran: 1x, jam konfigurabel default 08:45 (15 menit
   sebelum mulai) dan hanya pada `workdays`.

## 8. Risiko

- **Risiko terbesar: perilaku absensi berubah tanpa disadari.** Mitigasi: default `off`/`mark`,
  grace 10 menit, dan tes yang mengunci perilaku lama saat setting kosong.
- **Checkpoint disalahgunakan** (diisi belakangan untuk menutup absen). Mitigasi: batas 7 hari,
  alasan wajib, jejak penyetuju, dan laporan "checkpoint bulan ini" untuk HR.
- **Jam kerja global** menghambat klien multi-shift. Mitigasi: siapkan kolom per lokasi di fase shift,
  jangan paksakan sekarang.
- **Reminder lokal tidak andal** (app harus pernah dibuka). Mitigasi: dokumentasikan, dan siapkan
  E3 untuk push server-side.
